# test-review-dojo

テストを「書く側」の考え方を体系的に学び、その結果として
**AI が書いたテストを自分の頭で評価できるようになる** ための学習リポジトリ。

## このリポジトリの考え方

AI のテストをレビューできない原因は「穴の見つけ方を知らない」ことではなく、
**「よいテストとは何か」という基準を自分が持っていない**ことにある。
基準があれば、レビューで聞くべき質問は自然に出てくる。

そこで、専門家がテストを設計するときの考え方を、次の順に積み上げる。

1. **なぜ** テストを書くのか（目的と価値の基準）
2. **どこで** テストするのか（テストのレベルと範囲）
3. **何を** テストするのか（テストケース設計技法）
4. **どう** 書くのか（構造・検証・テストダブル）
5. **どれくらい** 足りているのか（品質の測り方）
6. 以上を **レビューの観点** に変換する

## ロードマップ

| # | 章 | 学ぶこと | この章のあと言えるようになること | 状態 |
|---|---|---|---|---|
| 1 | [テストの目的と価値](docs/01-purpose-and-value.md) | よいテストの 4 本柱 | 「このテストは何を守っているの？」 | ✅ |
| 2 | テストのレベルと範囲 | 単体 / 結合 / E2E、テストピラミッド | 「これは単体で見るべき？結合で見るべき？」 | ⬜ |
| 3 | テストケース設計技法 | 同値分割、境界値分析、デシジョンテーブル、状態遷移 | 「境界値は網羅されてる？」 | ⬜ |
| 4 | テストの構造 | AAA パターン、命名、1 テスト 1 振る舞い | 「このテスト名で何が壊れたか分かる？」 | ⬜ |
| 5 | 何を検証するか | 振る舞い vs 実装詳細、アサーションの強さ | 「実装を変えたら壊れない？」 | ⬜ |
| 6 | テストダブル | スタブ / モック / フェイク / スパイ、モックしすぎ問題 | 「このモックは必要？」 | ⬜ |
| 7 | テストの質を測る | カバレッジの限界、ミューテーションテスト | 「カバレッジ 100% は安心していい？」 | ⬜ |
| 8 | TDD | Red → Green → Refactor | テストから設計を考える | ⬜ |
| 9 | AI のテストをレビューする | 1〜8 章の観点をチェックリスト化 | AI に具体的な修正指示を出す | ⬜ |

各章は **解説（docs/）** と **動かせるサンプル（examples/）** のセットで構成する。
章は 1 つずつ、理解を確認しながら追加していく。

## 参考にしている考え方

- Vladimir Khorikov『単体テストの考え方/使い方』（Unit Testing Principles, Practices, and Patterns）
- JSTQB / ISTQB Foundation Level シラバス（テスト設計技法）
- Kent Beck『テスト駆動開発』

## サンプルの動かし方

```bash
pnpm install
pnpm test            # 全サンプルのテストを実行
pnpm test examples/ch01   # 章ごとに実行
```

技術スタックは [dots-war-sim](https://github.com/matun02/dots-war-sim) と同じ
TypeScript + Vitest。ここで学んだことはそのまま実プロジェクトに持ち込める。
