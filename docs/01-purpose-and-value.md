# 第1章 テストの目的と価値

> この章のゴール: 「テストが通っている」と「テストに価値がある」は別物だと理解し、
> テストの価値を測る **4 つの基準** を自分の言葉で説明できるようになる。

---

## 1. テストは何のためにあるのか

テストの目的は「コードが正しいことを証明する」ことではない（それは原理的に不可能）。
専門家の答えは次のとおり。

> **テストの目的は、ソフトウェアを変更し続けても壊れないようにすること**
> ＝ 持続可能な開発を支えること。

コードは書いて終わりではなく、機能追加・バグ修正・リファクタリングで何度も変更される。
変更のたびに「どこか壊れていないか」を人間が手で確かめるのは不可能なので、
その確認を自動化したものがテスト。

だからテストを評価するときの問いは、常にこれになる。

> **「このテストは、将来コードを変更するときに役立つか？」**

### テストはタダではない

テストもコード。書くコスト、読むコスト、直すコスト、実行時間がかかる。
価値の低いテストは **ないほうがマシ** なことすらある。

- 何も守っていないのに、緑色に光って「安心感」だけを与える
- 正しいリファクタリングをするたびに壊れて、直す手間だけかかる

AI はテストを大量に、速く書ける。だからこそ **「数」ではなく「1 本ごとの価値」** で
判断する基準が必要になる。

## 2. よいテストの 4 本柱

Vladimir Khorikov は、テストの価値を次の 4 つの基準で整理している。

| 柱 | 意味 | 欠けているとどうなるか |
|---|---|---|
| ① **回帰に対する保護** | バグが入ったときに、ちゃんと失敗するか | バグがあっても緑のまま（**偽陰性**） |
| ② **リファクタリングへの耐性** | 振る舞いを変えない変更では、失敗しないか | 正しい変更なのに赤くなる（**偽陽性**） |
| ③ **迅速なフィードバック** | すぐに結果が返ってくるか | 実行されなくなる |
| ④ **保守のしやすさ** | 読みやすく、動かしやすいか | 誰も直せなくなる |

### ① 回帰に対する保護

「回帰（regression）」= 以前は動いていた機能が、変更によって壊れること。
テストがどれだけ回帰を検知できるかは、主に次で決まる。

- テストが **実行するコードの量**
- そのコードの **重要さ**（ビジネス上の大事なルールか）
- 期待値が **仕様から独立して決まっているか**（後述のテスト B がこれに失敗している）

### ② リファクタリングへの耐性

リファクタリング = **外から見た振る舞いを変えずに** 内部の構造を変えること。
振る舞いが変わっていないのにテストが落ちるのは「誤報（偽陽性）」。

誤報が多いと何が起きるか:

1. 開発者は「どうせまたテストの問題でしょ」とテストの失敗を信用しなくなる
2. 本物のバグで落ちても見逃す
3. リファクタリング自体を避けるようになり、コードが劣化する

偽陽性の原因はほぼ 1 つ: **テストが「何をするか」ではなく「どうやっているか」を検証している**
こと（実装の詳細への依存）。

### ①と②は「どちらも大事」

| | テストが成功 | テストが失敗 |
|---|---|---|
| **コードが正しい** | ✅ 正しい判定 | ❌ **偽陽性**（②が弱い） |
| **コードにバグがある** | ❌ **偽陰性**（①が弱い） | ✅ 正しい判定 |

- 偽陰性（バグを見逃す）は、すぐに気づける害
- 偽陽性（誤報）は、ゆっくり効いてくる害。プロジェクトが大きくなるほど深刻になる

初心者が見落としやすいのは偽陽性のほう。「細かく検証しているほど良いテスト」と思いがちだが、
細かく検証しすぎると実装の詳細に依存して②を失う。

### ③④は前提条件

③ 迅速なフィードバックと ④ 保守のしやすさは、①②を活かすための前提。
どんなに正確なテストでも、実行に 10 分かかったり、読んでも意図が分からなかったりすれば
使われなくなる。（③は第2章「テストのレベル」で、④は第4章「テストの構造」で詳しく扱う）

## 3. 実例で確かめる

`examples/ch01/` に、同じ関数に対する 3 種類のテストがある。**3 つとも緑（成功）** になる。

### 対象の仕様

> 会員、または小計 5000 円以上なら送料無料。それ以外は送料 500 円。

- [`rules.ts`](../examples/ch01/rules.ts) — 送料無料の判定 `isFreeShipping`
- [`shipping.ts`](../examples/ch01/shipping.ts) — 送料を返す `shippingFee`

### 3 つのテスト

| テスト | 書き方 |
|---|---|
| [A](../examples/ch01/a-spec-by-example.test.ts) | 仕様を **具体的な値** で書く（4999 円 → 500 円、など） |
| [B](../examples/ch01/b-tautology.test.ts) | 期待値を **実装と同じ定数・計算** から作る |
| [C](../examples/ch01/c-implementation-coupled.test.ts) | 内部の関数を **モック** して、その **呼ばれ方** を検証する |

B と C は、AI がとてもよく書くパターン。一見ちゃんとしていて、どちらも緑になる。

### 実験：コードを変えて、どのテストが反応するかを見る

| 実験 | 変更内容 | 正しい変更？ | A | B | C |
|---|---|---|---|---|---|
| 1 | `FREE_THRESHOLD` を `5000` → `50000` に（仕様違反） | ❌ バグ | **落ちる** ✅ | 通る 😱 | 通る 😱 |
| 2 | `isFreeShipping` を使わず `shipping.ts` の中に条件を直接書く | ✅ リファクタ | 通る ✅ | 通る ✅ | **落ちる** 😱 |
| 3 | 会員判定 `order.isMember \|\|` を消す（仕様違反） | ❌ バグ | **落ちる** ✅ | 通る 😱 | 通る 😱 |

（このリポジトリで実際に変更して実行した結果）

### なぜこうなるのか

**B: 実装をなぞるテスト（トートロジー）→ ① 回帰に対する保護が弱い**

B は期待値を `FREE_THRESHOLD` から計算している。
定数そのものが間違っていたら、テストの期待値も一緒に間違う。
「実装が自分自身と一致すること」を確かめているだけで、**仕様** と照らし合わせていない。

> 期待値は、実装とは独立した情報源（仕様書、ドメインの知識、手計算）から決める。
> だから A のように `5000` や `500` といった **リテラル（具体的な値）** を書くのが基本。

また、B には会員のケースがないので、実験 3 にも反応しない（これは第3章「テストケース設計」の話）。

**C: 実装の詳細に依存するテスト → ① と ② の両方が弱い**

C は `isFreeShipping` をモックで置き換えている。そのため

- 本物の判定ロジックが **一度も実行されない** → 判定のバグに気づけない（実験 1, 3）
- 「`isFreeShipping` を呼ぶ」という **内部のやり方** を検証している → やり方を変えると落ちる（実験 2）

`shippingFee` を使う側にとって大事なのは「いくら返るか」だけ。
「内部でどの関数を何回呼んだか」は利用者から見えない実装の詳細であり、検証すべきではない。
（モックをいつ使うべきかは第6章「テストダブル」で扱う）

**A: 仕様を具体値で書くテスト → ①② ともに強い**

A は「この入力なら、この出力」という **外から見える振る舞い** だけを検証している。
だから、内部の作りを変えても落ちず（②）、振る舞いが壊れたら落ちる（①）。

### 自分で確かめる

```bash
pnpm install
pnpm test examples/ch01
```

上の実験の変更を `examples/ch01/` のファイルに手で加えて、もう一度 `pnpm test examples/ch01` を実行する。
（終わったら `git checkout examples/ch01` で元に戻せる）

## 4. この章で手に入れた「レビューの問い」

AI が書いたテストを見たとき、まずこの 3 つを聞く。

1. **このテストは、どんなバグが入ったら落ちる？**（①）
   - 具体的に 1 つも思いつかないなら、そのテストは何も守っていない可能性がある
2. **振る舞いを変えずに中身を書き換えたら、このテストは落ちる？**（②）
   - 落ちるなら、実装の詳細を検証している
3. **期待値はどこから来た？**（①）
   - 実装と同じ定数や計算から来ているなら、トートロジーを疑う

AI に聞くときは、例えばこう聞ける。

> 「このテストが検知できるバグの例を 3 つ挙げて。逆に、検知できないバグはある？」
> 「`shippingFee` の内部実装をリファクタリングしたとき、どのテストが落ちる？」
